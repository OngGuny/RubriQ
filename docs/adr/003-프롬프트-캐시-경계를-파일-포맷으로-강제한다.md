# 003. 프롬프트의 캐시 경계를 파일 포맷으로 강제한다

- 상태: 채택
- 날짜: 2026-09-07

## 맥락

프롬프트 캐싱은 **프리픽스 매칭**이다. 앞부분이 1바이트라도 달라지면 그 뒤가 전부 캐시 미스다.
그런데 캐시 미스는 **에러를 내지 않는다.** 조용히 비용만 오른다.

이 프로젝트는 항목별 분리 호출로 호출 횟수가 6배가 되고, 그 비용을 캐싱으로 상쇄하는 설계다
(설계 문서 §1). 캐싱이 조용히 죽으면 설계의 절반이 무너지는데 아무도 모른다.

## 선택지

- **A) 관례로 지킨다** — "가변 내용은 뒤에 두자"고 문서에 적고 리뷰에서 본다.
  가볍지만, 몇 주 뒤의 내가 지킬 거라는 보장이 없다.
- **B) 파일 포맷으로 강제한다** — 프롬프트 파일에 `<!-- CACHE_BOUNDARY -->` 마커를 두고,
  로더가 경계 앞뒤를 나눈다. 가변 슬롯 `{{ESSAY}}`가 경계 **앞**에 있으면 로딩 자체를 실패시킨다.

## 결정

**B.** `src/rubriq/prompts/registry.py`가 로딩 시점에 검사한다.
`tests/unit/test_prompts.py::TestCacheBoundary`가 이 규칙들을 고정한다.

추가로 `Prompt.fingerprint`(내용 SHA256 앞 12자)를 둔다.
버전 문자열을 안 올리고 내용만 고친 경우를 잡기 위해서다 —
측정 결과와 프롬프트를 대조할 때 버전만 믿으면 조용히 틀린 결론을 낸다.

## 트레이드오프

- 프롬프트 파일에 마커라는 **비표준 문법**이 생긴다. Langfuse에 등록할 때 마커를 어떻게
  다룰지 별도 결정이 필요하다 (아직 미정).
- 경계가 하나뿐이라 breakpoint를 여러 개 두는 고급 캐싱 전략은 못 쓴다.
  현재 구조(고정 루브릭 + 가변 에세이)에는 충분하지만, T1에서 앵커를 붙이면
  "루브릭은 항상 고정 / 앵커는 에세이마다 다름"이라 경계가 하나로는 부족해질 수 있다.

## 되돌리는 조건

앵커 검색이 붙어 캐시 가능한 블록이 2단계 이상으로 갈리면(루브릭 고정 → 앵커 준고정 → 에세이 가변),
마커를 복수 경계로 확장하거나 프롬프트를 조립식 빌더로 바꾼다.

## 알아둘 것: 최소 캐시 프리픽스는 모델마다 다르다

| 모델 | 최소 |
|---|---:|
| Claude Opus 5 | 512 토큰 |
| Claude Sonnet 5, Opus 4.8 | 1024 토큰 |
| **Haiku 4.5** | **4096 토큰** |

세대 순이 아니다. 현재 system 블록은 약 900토큰이라 **Opus 5에서는 캐시되지만
Haiku 4.5에서는 조용히 캐시되지 않는다.**

T2의 모델 라우팅에서 "싼 항목은 Haiku로"를 하면 **캐시 이득이 사라져 오히려 비쌀 수 있다.**
라우팅 비용 계산에 이걸 반드시 포함한다. `usage.cache_read_input_tokens`가 0인지 확인하는 게
유일한 검증 수단이다.
