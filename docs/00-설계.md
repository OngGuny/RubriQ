# RubriQ 설계 문서

> 루브릭 기반 영어 Writing 자동 평가 파이프라인 · 개인 프로젝트
> 범위·근거·계획의 단일 진실 공급원(SSOT)
> 기능 단위 기획은 [`docs/features/`](features/) — 17개 기능의 문제·계약·설계·실패 모드

---

## 0. 이 프로젝트의 목표

**SOTA 채점기를 만드는 것이 아니다.**

목표는 **측정 가능(measurable)하고 관측 가능(observable)한 채점 파이프라인**을 직접 구현하고
숫자를 남기는 것이다. LLM 애플리케이션에서 "좋아졌다"는 말은 측정 없이는 주장에 불과하다.
이 프로젝트는 그 측정 체계를 먼저 세우고, 그 위에서 개선을 검증한다.

구체적으로 확인하려는 것:

- 루브릭 기반 평가 파이프라인을 그래프로 설계했을 때 단일 프롬프트 대비 무엇이 나아지는가
- 그 개선을 **재현 가능한 지표**로 어떻게 증명하는가 (QWK · 일관성 · latency · 비용)
- 프롬프트·모델을 바꿨을 때 성능 저하를 **CI에서 자동으로 잡는** 체계는 어떻게 생겼는가

**정직성 원칙**: 이건 개인 프로젝트다. 실무 시스템으로 포장하지 않는다.
한계와 실패는 `docs/failures/`에 먼저 쓴다.

## 1. 시스템 정의

학생이 제출한 영어 에세이를 받아 **루브릭 항목별 점수 + 근거 + 교사용 코멘트**를 반환한다.

```
에세이 입력
  → [전처리]  정규화 · 언어 판별 · 분량 검사
  → [사전 라우팅]  조기 반환 케이스 분기 (분량 미달 / 주제 이탈 / 비영어)
  → [분석 도구 병렬 호출]
        ├ grammar_check     문법·철자 오류 목록
        ├ lexical_stats     어휘 다양성 · CEFR 레벨 추정
        └ retrieve_anchors  루브릭 앵커 에세이 RAG 검색 (pgvector)
  → [루브릭 채점]  항목별 병렬 LLM 호출, 각 점수마다 본문 근거 인용 강제
  → [일관성 검증]  항목 간 모순 탐지 → 조건부 재채점 루프 (최대 2회)
  → [피드백 생성]  학년 · 과제유형별 프롬프트로 교사용 코멘트 작성
  → [후처리]  Pydantic 스키마 검증, 실패 시 복구 재시도
  → 응답 (스트리밍)
```

### 설계 근거

- **왜 단일 프롬프트가 아니라 그래프인가** — 루브릭 6개 항목을 한 번에 채점시키면
  항목 간 점수가 서로 오염된다(문법 점수가 낮으면 내용 점수도 끌려 내려가는 **후광 효과**).
  항목별로 분리 호출하고, 대신 **일관성 검증 노드**를 따로 둬서 모순을 잡는다.
  분리의 대가는 토큰 비용이고, 그 대가를 상쇄하는 게 프롬프트 캐싱이다.
- **왜 도구 호출을 쓰는가** — 철자·문법 오류 카운트 같은 결정적(deterministic) 정보를
  LLM에게 세게 하는 것은 낭비이고 부정확하다. 규칙 기반 도구가 뽑은 사실을
  컨텍스트로 넣고, LLM은 **판단**만 하게 한다.
- **왜 앵커 에세이를 검색하는가** — 루브릭 점수는 상대 기준이다. 앵커(각 점수대 대표 답안)를
  few-shot으로 붙이면 채점 분산이 줄어든다.
- **왜 재채점을 무한 루프로 두지 않는가** — 수렴 보장이 없고 latency가 폭발한다.
  최대 2회로 제한하고, 그래도 모순이면 `needs_human_review` 플래그를 세워 반환한다.
  **실패를 숨기지 않고 사람에게 넘기는 설계**가 교육 도메인에서는 더 안전하다.

## 2. 데이터셋

공개 영어 에세이 채점 데이터를 골든셋으로 쓴다.

| 후보 | 특성 | 판단 |
|---|---|---|
| **ELLIPSE / Feedback Prize - ELL** (Kaggle) | ESL 학습자 에세이 + 6개 분석적 루브릭 항목 각 1~5점 | **1순위.** 루브릭 구조가 그대로 있음 |
| ASAP-AES (Hewlett) | 총점 위주, 프롬프트 8종 | 2순위. 항목별 점수 부족 |
| 직접 생성 | LLM으로 합성 에세이 + 수동 라벨 | 보조. 엣지 케이스용 |

- **골든셋 규모**: 50~100건이면 충분하다. 통계적 유의성이 목적이 아니라
  **회귀 감지**가 목적이다. 절대 성능을 주장하는 데는 쓰지 않는다.
- 라이선스는 반드시 확인하고 `eval/golden/LICENSE.md`에 명시한다.
  상업적 사용·재배포 제한이 있으면 원문은 커밋하지 않고 지표만 인용한다.

## 3. 측정 지표

이 프로젝트의 핵심 산출물.

| 지표 | 정의 | 왜 이걸 보는가 |
|---|---|---|
| **QWK** (Quadratic Weighted Kappa) | 인간 채점 대비 일치도 | 자동 채점의 표준 지표. 순서형 점수라 정확도(accuracy)로는 부족 |
| **인접 정확도** | \|예측 − 정답\| ≤ 1 비율 | 실무 수용 기준. 1점 차이는 교사도 갈린다 |
| **일관성 σ** | 동일 입력 5회 반복 시 점수 표준편차 | temperature 0에서도 흔들린다 |
| **오류 탐지 P/R/F1** | 문법 오류 지적의 정밀도·재현율 | 헛짚은 지적(오탐)이 교육에서는 치명적 → F0.5로 precision 가중 |
| **p50 / p95 latency** | 응답 시간 | 꼬리 지연이 체감 지연이다 |
| **에세이당 비용** | 토큰 × 단가 | 분리 호출의 대가를 정량화 |

**측정 없는 개선은 주장이다.** 모든 개선 항목은 `docs/results/`에 before/after 표로 남긴다.

## 4. 단계별 실행 계획

- [ ] 골든셋 50건 확보 · 루브릭 정의 문서화

- [x] 단일 프롬프트 베이스라인 채점기 (LLM 1회 호출, 구조화 출력)

## 5. 기술 스택 선택과 근거

| 영역 | 선택 | 근거 |
|---|---|---|
| Agent | **LangGraph** | 상태 그래프가 채점 워크플로우와 구조적으로 맞음 (조건 분기 + 루프) |
| 관측 | **Langfuse v4** | self-host. SDK v3+ 는 v2 서버와 통신 불가 (ADR 004) |
| 서빙 | FastAPI (async) | LLM 호출은 I/O 대기가 지배적이라 async로 동시성을 번다 |
| 구조화 출력 | Pydantic v2 | 후처리 스키마 검증 + 실패 복구 |
| 벡터 검색 | pgvector | 앵커 에세이 검색 |
| 모델 | Anthropic + 추가 벤더 1종 | 라우팅 비교용 |
| 테스트 | pytest + GitHub Actions | 회귀 게이트를 CI에 붙인다 |
| 문법 도구 | LanguageTool (로컬) 또는 규칙 기반 | 결정적 도구와 LLM 판단의 역할 분리 |

## 6. 의도적으로 하지 않는 것

범위를 지키기 위해 명시해 둔다.

- **모델 파인튜닝** — 골든셋 50건 규모에서 파인튜닝은 과적합이 더 큰 위험이다.
  프롬프트·앵커 튜닝으로 얻을 수 있는 개선이 먼저다.
- **Speaking 평가** — 음성 처리는 별개 축이라 범위를 넓히면 아무것도 못 끝낸다.
  Writing에서 확립한 루브릭 파이프라인이 Speaking에도 전이된다는 설계로 갈음한다.
- **프론트엔드** — 이 프로젝트가 증명하려는 축이 아니다.
- **완전 자동화된 재학습** — 데이터 유입이 없는 개인 프로젝트에서는 형식만 남는다.

## 7. 알려진 한계

먼저 적어둔다. 진행하며 `docs/failures/`로 옮긴다.

- **루브릭 정합성 미검증** — 골든셋의 정답 점수는 원 데이터셋 애너테이터의 루브릭으로 매겨졌다.
  내 루브릭이 그것과 다르면 QWK 하락을 모델 성능 문제로 오진하게 된다. (ADR 001)
- **베이스라인이 의도적으로 약하다** — 개선폭이 과대평가된다. (ADR 002)
- **회귀 임계치에 근거가 없다** — 인간 채점자 간 일치도(IAA)를 모르기 때문이다.
  베이스라인 실측 후 상대 기준으로 바꿀 계획이다.
- **골든셋 과적합 위험** — holdout 분리를 아직 하지 않았다.
