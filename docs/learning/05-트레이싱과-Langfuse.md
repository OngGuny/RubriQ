# 트레이싱과 Langfuse

## 한 줄

**트레이싱**: 요청 하나가 시스템을 통과하는 전 과정을 기록하는 것.
**Langfuse**: LLM 앱 전용 트레이싱 도구.

---

## 문제부터 — LLM 앱은 왜 디버깅이 어려운가

채점기가 엉뚱한 점수를 냈다. 어디가 문제인가?

```
에세이 → 전처리 → 도구 3종 → 항목별 채점 6회 → 일관성 검증 → 피드백
```

후보가 **최소 11군데**다. 전처리가 글자를 깨뜨렸나? 문법 도구가 오류를 못 잡았나?
채점 프롬프트가 나쁜가? 6개 중 하나만 이상한가? 재채점 루프가 오히려 망쳤나?

일반 웹 서비스라면 로그를 보면 된다. 그런데 LLM 앱에는 세 가지가 더 있다.

| | 일반 서비스 | LLM 앱 |
|---|---|---|
| 재현 | 같은 입력 → 같은 출력 | **같은 입력 → 다른 출력** |
| 재실행 | 공짜 | **돈이 든다** |
| 실패 | 예외가 터짐 | **그럴듯한 오답이 조용히 나옴** |

`print()`로 될 일이 아니다. **문제가 생긴 그 순간의 전체 맥락**이 남아 있어야 한다.
다시 돌려서 재현할 수 없기 때문이다.

---

## 로그와 트레이스는 다르다

**로그**는 사건의 나열이다.

```
12:01:03  채점 시작 e-042
12:01:05  문법 오류 7개 발견
12:01:19  grammar=2
12:01:19  vocabulary=4
12:01:31  모순 감지: |grammar - conventions| = 3
```

읽을 수는 있지만 **구조가 없다.** 동시에 여러 요청이 돌면 뒤섞이고,
"이 줄과 저 줄이 같은 요청인가"를 눈으로 맞춰야 한다.

**트레이스**는 나무 구조다.

```
trace: grade:e-042                        2.4초  $0.007
├─ span: 전처리                            0.01초
├─ span: 도구 호출                         0.8초
│  ├─ span: grammar_check                 0.8초   오류 7개
│  └─ span: lexical_stats                 0.02초
├─ generation: score:grammar              1.1초  $0.001  입력 1,700 출력 210
├─ generation: score:vocabulary           0.9초  $0.001
│  ... (6개)
└─ span: 일관성 검증                        0.01초  모순 1건 → 재채점
```

**부모-자식 관계**와 **시간**이 들어 있다. 어디서 시간을 썼는지, 어느 단계에서
값이 이상해졌는지가 한 눈에 보인다.

### 용어 세 개

| 용어 | 뜻 | 예 |
|---|---|---|
| **trace** | 요청 하나 전체 | 에세이 1건 채점 |
| **span** | 그 안의 한 구간 | 전처리, 도구 호출 |
| **generation** | LLM 호출인 span | 항목별 채점 1회 |

`generation`이 따로 있는 게 LLM 도구의 특징이다.
일반 span에는 없는 것들이 붙는다 — **모델명, 입력/출력 토큰, 비용, 프롬프트 버전**.

---

## Langfuse가 하는 일

트레이싱만 하는 게 아니다. 네 가지를 묶어준다.

| 기능 | 하는 일 |
|---|---|
| **트레이싱** | 위의 나무 구조를 저장하고 UI로 보여준다 |
| **프롬프트 버전 관리** | 프롬프트를 등록하고, 어떤 호출이 어떤 버전을 썼는지 잇는다 |
| **비용 집계** | 토큰 × 단가를 자동 계산. 모델별·기간별 집계 |
| **평가 연결** | 트레이스에 점수를 붙여 "이 응답이 좋았나"를 추적 |

**self-host가 가능하다.** `docker compose`로 띄우면 무료다.
데이터가 내 서버에만 남는다는 뜻이기도 하다 — 학생 글을 다루는 이 프로젝트에서는 중요하다.

경쟁 도구로 LangSmith(LangChain 제작), Braintrust, Arize Phoenix 등이 있다.
Langfuse를 고른 이유는 self-host가 되고 오픈소스라서다.

## 이 프로젝트에서 왜 필요한가

세 가지 질문에 답하기 위해서다. **트레이스 없이는 셋 다 답할 수 없다.**

### 1. "어디서 무너졌나"

QWK가 낮게 나왔을 때, 최종 점수만 보면 원인을 모른다.
트레이스를 열면 6개 generation 중 어느 것이 이상한지, 도구 출력이 제대로
들어갔는지, 재채점 루프가 발동했는지가 보인다.

> F08 문서에 이렇게 적어뒀다 — **"트레이스를 붙였다"가 아니라
> "트레이스로 원인을 찾았다"가 이 기능의 완료 조건이다.**

### 2. "캐시가 실제로 먹고 있나"

프롬프트 캐싱은 **실패해도 에러를 내지 않는다.** 조용히 비용만 오른다.
확인할 방법은 응답의 `cache_read_input_tokens`가 0인지 보는 것뿐이다.

트레이스에 이 값을 남기지 않으면 **캐싱이 죽은 걸 영원히 모른다.**

### 3. "어떤 프롬프트로 나온 숫자인가"

프롬프트를 v1 → v2로 고치고 QWK가 올랐다면, 그게 프롬프트 덕인지 확인해야 한다.
트레이스마다 `prompt_id`와 내용 지문이 남아 있으면 결과표와 대조할 수 있다.

## 함정 1 — 관측이 본 기능을 죽이면 안 된다

트레이싱은 **부가 기능**이다. Langfuse가 죽었다고 채점이 멈추면 안 된다.

이 프로젝트는 모든 관측 실패를 삼킨다 — 키가 없거나, 서버가 죽었거나,
span 생성이 실패하거나, 업데이트가 터져도 채점은 계속된다.

**단 비활성화됐다는 사실은 로그에 남긴다.**

> 조용히 꺼진 관측은 없는 것보다 나쁘다. 있다고 믿게 만들기 때문이다.

## 함정 2 — 테스트가 관측 저장소를 오염시킨다

**실제로 밟았다.** `.env`에 키를 넣자마자 단위 테스트가 진짜 Langfuse로
트레이스를 보내기 시작했다. `grade:e-001` 트레이스 5건이 쌓인 걸 보고 알았다.

테스트 코드가 채점기를 만들면 → 채점기가 전역 트레이서를 잡고 → 진짜로 전송한다.

대응은 두 가지다.

1. 테스트에서 트레이서를 **강제로 비활성화**한다 (autouse fixture)
2. 검증 방법을 고정한다 — **테스트 전후 이벤트 수가 같은지** 확인

> 테스트를 돌릴 때마다 관측 데이터가 더러워지면, 트레이스를 믿을 수 없게 된다.
> 그러면 관측의 목적 자체가 사라진다.

## 함정 3 — 무엇을 남기지 않을지 먼저 정한다

트레이스에 입력과 출력을 통째로 남기는 게 기본값인 도구가 많다.
편하지만 위험하다. 이 프로젝트의 입력은 **학생이 쓴 글**이다.

기본값을 "남기지 않음"으로 뒀다. 트레이스에는 `essay_id`와 통계(길이·단어 수)만
들어가고, 본문은 디버깅할 때만 켠다. `essay_id`로 원본을 되찾을 수 있으니
관측 저장소에 복제할 이유가 없다.

지금은 공개 데이터셋만 쓰지만 **처음부터** 이렇게 정해뒀다.
나중에 고치려면 이미 쌓인 데이터를 지워야 한다.

## 함정 4 — 서버 버전과 SDK 버전을 맞춰야 한다

**이것도 실제로 밟았다.** 서버를 v2로 띄워두고 SDK 4.x를 붙이려다 막혔다.

```
auth_check: ValidationError — Projects.data.0.organization Field required
```

Langfuse SDK는 v3부터 **OpenTelemetry 기반으로 재작성**됐다.
API 응답 스키마부터 다르고 메서드 이름도 바뀌었다. v2 서버와는 통신이 안 된다.

서버를 v4로 올렸는데, 대가가 있었다 — v2는 컨테이너 2개면 됐지만
v4는 **6개**를 요구한다(web · worker · postgres · ClickHouse · Redis · MinIO).
트레이스를 ClickHouse에 넣고 큐로 비동기 수집하는 구조라서다.

> 자세한 판단 근거는 [ADR 004](../adr/004-Langfuse-v4로-올리고-SDK를-맞춘다.md).

---

## OpenTelemetry는 뭔가

SDK v3부터 Langfuse가 그 위에 얹혔다고 했는데, **OpenTelemetry(OTel)** 는
트레이싱의 **업계 표준 규격**이다. 특정 회사 도구가 아니라 벤더 중립 표준이다.

의미: 코드를 OTel 방식으로 계측해두면 **백엔드를 바꿔도 계측 코드는 그대로**다.
Langfuse가 마음에 안 들면 다른 도구로 옮길 수 있다.

이 프로젝트는 그걸 한 겹 더 감쌌다 — `LangfuseTracer` 파사드를 두고
채점기는 그 뒤만 본다. 도구를 바꿀 때 고칠 파일이 하나다.

---

## 한 줄 요약

> 트레이싱은 **다시 돌려볼 수 없는 것을 기록해두는 일**이다.
> LLM 앱은 같은 입력에 같은 출력이 안 나오고 재실행에 돈이 드니,
> 문제가 생긴 그 순간이 남아 있지 않으면 원인을 찾을 방법이 없다.
