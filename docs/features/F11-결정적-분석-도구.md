# F11. 결정적 분석 도구 (grammar_check · lexical_stats)

| | |
|---|---|
| 상태 | **미구현** |
| 단계 | T1 |
| 예정 코드 | `src/rubriq/tools/grammar_check.py` · `lexical_stats.py` |
| 의존 | F01 데이터 계약 |

## 문제

**철자·문법 오류 개수를 LLM에게 세게 하는 것은 낭비이고 부정확하다.**
LLM은 "오류가 몇 개인가"를 잘 못 세고, 셀 때마다 답이 다르다.

## 설계 원칙 — 사실과 판단을 분리한다

```
규칙 기반 도구: "이 문장의 이 위치에 시제 오류가 있다"   ← 사실
LLM:            "이 정도 오류가 이해를 얼마나 방해하는가"  ← 판단
```

도구가 뽑은 사실을 컨텍스트로 넣고 LLM은 **판단만** 한다.

## 계약

```python
grammar_check(text: str) -> list[GrammarError]
# GrammarError: start · end · rule_id · message · suggestion?

lexical_stats(text: str) -> LexicalStats
# type_token_ratio · avg_word_length · avg_sentence_length
# cefr_estimate · rare_word_ratio
```

둘 다 **순수 함수**다. 네트워크·LLM 호출 없음 → 테스트가 결정적이다.

## grammar_check 설계

| 항목 | 선택 |
|---|---|
| 엔진 | LanguageTool 로컬 (`language-tool-python`) |
| 동기/비동기 | **동기 라이브러리** — async 노드에서 스레드풀로 오프로드 |
| 실패 처리 | 도구 실패 시 빈 목록 + 플래그, 채점은 계속 |

**동기 블로킹이 이 프로젝트의 실제 사례다.** LanguageTool은 동기이고,
async 엔드포인트(F17)에서 그냥 호출하면 이벤트 루프가 막혀
그 워커의 모든 요청이 함께 지연된다. `asyncio.to_thread`로 오프로드한다.

## lexical_stats 설계

| 지표 | 정의 | 주의 |
|---|---|---|
| TTR | 고유 단어 / 전체 단어 | **길이에 민감** — 긴 글일수록 낮아진다 |
| CEFR 추정 | 빈도 목록 기반 대역 판정 | 어휘 목록 출처를 명시할 것 |

**TTR을 그대로 쓰면 분량이 긴 글에 불리하다.** 길이 보정(MTLD 등)을 검토하거나,
최소한 이 편향을 문서에 적고 LLM 프롬프트에 "길이 보정 없음"을 명시한다.

## 핵심 결정 — graceful degradation

```
도구 호출 실패 → 1회 재시도 → 또 실패 → 그 도구를 빼고 진행
```

도구 하나가 죽었다고 채점 전체가 죽으면 안 된다.
단 **어떤 도구가 빠졌는지 상태에 기록**하고, 그 사실이 결과에 남는다.

## 실패 모드

| 상황 | 처리 |
|---|---|
| LanguageTool 미설치/기동 실패 | 빈 목록 + `tool_degraded` 플래그 |
| 매우 긴 입력 | 길이 상한 후 잘라내되 **잘랐다는 사실을 기록** |
| 오탐 과다 | 규칙 ID별 필터링 — 어떤 규칙을 껐는지 문서화 |

## 측정

`grammar_check` 출력 대 인간 라벨의 **P/R/F1**, 특히 **F0.5**(precision 가중).
없는 오류를 지적하면 학생이 잘못 배운다 — 오탐이 미탐보다 비싸다.
