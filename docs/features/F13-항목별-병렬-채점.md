## 문제 — 후광 효과 (halo effect)

루브릭 6개 항목을 한 번에 채점시키면 **항목 간 점수가 서로 오염된다.**

> 문법 오류가 눈에 확 띈다 → "글이 엉망이네" → 어휘도 2점, 응집성도 2점

실제로는 어휘가 3점인데 문법에 끌려 내려간 것이다.
사람도 그러고, **LLM은 더 심하다** — 한 번의 호출로 6개를 다 달라고 하면
먼저 생성된 낮은 점수가 뒤따르는 점수를 끌어당긴다.

## 계약

```
입력: normalized_text · grammar_errors · lexical · anchors
출력: scores: dict[RubricDimension, DimensionScore]   (6개)
```

항목당 LLM 1회, **6개를 병렬 호출**한다.

## 설계

```
                ┌─ score(cohesion)     ─┐
                ├─ score(syntax)       ─┤
도구 출력 ──────┼─ score(vocabulary)   ─┼──→ scores
                ├─ score(phraseology)  ─┤
                ├─ score(grammar)      ─┤
                └─ score(conventions)  ─┘
```

각 호출은 **해당 항목의 루브릭만** 본다. 다른 항목의 점수를 모른다 —
모르면 오염될 수가 없다.

## 핵심 결정 1 — 도구 출력을 항목별로 골라 넣는다

| 항목 | 넣는 도구 출력 |
|---|---|
| Grammar | `grammar_errors` 전체 |
| Conventions | `grammar_errors` 중 철자·구두점 규칙만 |
| Vocabulary / Phraseology | `lexical` |
| Cohesion / Syntax | (도구 출력 없음) |

무관한 컨텍스트를 넣으면 토큰만 늘고 판단이 흐려진다.

## 핵심 결정 2 — 비용이 6배가 된다

이게 분리 호출의 **대가**다. 상쇄 수단은 프롬프트 캐싱(F04·F16)이다.
루브릭 고정부가 캐시되면 6회 호출의 증분은 항목별 가변부뿐이다.

**분리 호출과 캐싱은 한 쌍이다.** 캐싱 없이 분리만 하면 비용이 정당화되지 않는다.

## 핵심 결정 3 — latency는 오히려 줄 수 있다

6회 순차면 6배지만 **병렬이면 가장 느린 호출 하나**다.
단일 호출은 출력이 6배 길어 생성 시간이 길다.
→ p95가 어느 쪽이 나은지는 **측정해야 안다.** 예단하지 않는다.

## 실패 모드

| 상황 | 처리 |
|---|---|
| 6개 중 일부 실패 | 1회 재시도 → 또 실패하면 `needs_human_review` |
| 일부만 성공 | **부분 결과를 반환하지 않는다** — 6개가 다 있어야 유효(F01) |
| 전부 실패 | 채점 실패로 하네스에 보고 |
