## 문제

조건 분기와 루프가 있는 워크플로우에서 **어떤 노드가 무엇을 읽고 쓰는지**가
명시되지 않으면 디버깅이 불가능해진다.

## 계약 — 상태 스키마

```python
class GradingState(TypedDict):
    # 입력 (불변)
    essay: Essay
    # 전처리 산출
    normalized_text: str
    word_count: int
    language: str
    # 사전 라우팅
    early_return: EarlyReturnReason | None
    # 도구 출력
    grammar_errors: list[GrammarError]
    lexical: LexicalStats | None
    anchors: list[AnchorEssay]
    # 채점
    scores: dict[RubricDimension, DimensionScore]
    # 루프 제어
    regrade_count: int
    contradictions: list[str]
    needs_human_review: bool
    review_reason: str | None
```

## 핵심 결정 1 — 재시도 횟수를 상태에 넣는다

루프 종료 조건을 **노드 바깥이 아니라 상태로** 판단해야 그래프가 자기완결적이 된다.
외부 카운터로 제어하면 그래프만 봐서는 루프가 왜 끝나는지 알 수 없다.

## 핵심 결정 2 — 노드별 읽기/쓰기를 문서화한다

| 노드 | 읽기 | 쓰기 |
|---|---|---|
| 전처리 | `essay` | `normalized_text` `word_count` `language` |
| 사전 라우팅 | `word_count` `language` | `early_return` |
| 도구 3종 | `normalized_text` | `grammar_errors` `lexical` `anchors` |
| 항목별 채점 | 도구 출력 전부 | `scores` |
| 일관성 검증 | `scores` | `contradictions` `regrade_count` |

**읽기와 쓰기가 겹치는 노드를 만들지 않는다.** 겹치면 실행 순서에 결과가 의존한다.

## 핵심 결정 3 — 왜 LangGraph인가 (단점 포함)

**선택 이유**: 조건 분기와 루프가 있는 워크플로우에서 상태 전이를 명시적으로 그릴 수 있다.

**단점**: 추상화 레이어가 두꺼워 디버깅 시 내부를 뜯어봐야 한다.
단순 선형 파이프라인에는 과하다. 베이스라인(F06) 정도 복잡도였다면 직접 구현이 낫다.

프레임워크를 무비판적으로 옹호하지 않는다 — 이 프로젝트에서 정당화되는 건
**재채점 루프 + 조건 분기 + 병렬 노드**가 동시에 있기 때문이다.

## 그래프 형태

```
전처리 → 사전라우팅 ─조기반환→ [END]
              │
              └→ 도구3종(병렬) → 항목별채점(병렬) → 일관성검증
                                        ↑              │
                                        └──재채점(≤2)──┤
                                                       ↓
                                              피드백생성 → 후처리 → [END]
```
