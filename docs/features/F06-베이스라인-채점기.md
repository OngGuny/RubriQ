## 문제

이 프로젝트의 핵심 주장은 **"루브릭 항목을 분리 호출해야 한다"** 이다.
그 주장을 뒷받침할 **비교 대상**이 필요하다.

## 계약

`Grader` 프로토콜을 구현한다 — F13 그래프 채점기와 **동일한 인터페이스**라
같은 하네스에 물려 직접 비교할 수 있다.

```
grade(essay) -> GradingResult
```

LLM 1회 호출로 6개 항목을 한꺼번에 채점한다.

## 핵심 결정 — 일부러 약하게 만든다

튜닝하지 않는다. 코드 docstring에 **"일부러 만든 허수아비"** 라고 명시한다.

**트레이드오프**: 개선폭이 과대평가된다. Agent가 이긴 몫 중 얼마가 '분리 호출' 덕이고
얼마가 '베이스라인을 안 튜닝해서'인지 분리되지 않는다. 이건 실제 한계이고 README에 적는다.

이를 줄이려고 베이스라인도 **같은 루브릭·같은 프롬프트 파일**을 쓴다.
달라지는 건 호출 횟수(1회 vs 항목별)뿐이다 — 변수를 하나로 줄였다.

## 설계 — LLM 출력에 제약을 안 건다

```python
class LLMDimensionScore(BaseModel):
    score: int   # ge/le 없음 — 의도적
```

JSON 스키마로 모델을 묶는 대신 **범위를 벗어난 값을 관측**하고 싶다.
검증은 `DimensionScore`로 변환할 때 걸린다.

## 실패 모드

| 상황 | 처리 |
|---|---|
| 항목 누락 | `GradingError` — 누락 항목명 포함 |
| 점수 범위 밖 | `GradingError` |
| 근거 인용 없음 | `GradingError` |
| 인용이 원문에 없음 | **점수 유지 + `needs_human_review`** |

마지막 줄이 중요하다. 근거가 부실해도 점수 자체는 맞을 수 있고, 그 판단은 사람이 한다.

## 측정

`FakeLLM`으로 결정적 검증. 특히 **에세이가 캐시 프리픽스에 새지 않는지**를 테스트로 고정한다
(`test_essay_goes_into_user_block_not_system`).

## 지우지 말 것

비교 대상이 사라지면 개선폭을 말할 수 없다.
Agent가 베이스라인을 못 이기면 **"분리 호출이 이득이 없었다"를 결과로 기록**한다.
음성 결과도 측정 결과다.
