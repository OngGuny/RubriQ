## 문제

프롬프트나 모델을 바꿨을 때 **성능이 떨어진 걸 자동으로 잡아야 한다.**
사람이 눈으로 보는 체계는 결국 아무도 안 본다.

## 계약

```
Grader 프로토콜:  grade(essay: Essay) -> GradingResult
evaluate(grader, items) -> EvaluationReport
check_regression(report, threshold) -> list[str]   # 빈 리스트면 통과
```

## 설계

**게이트 로직을 채점기와 분리한다.** `check_regression`은 순수 함수라
LLM 없이 가짜 채점기로 검증할 수 있다.

```
FakeGrader(offset=0)  → 완벽한 채점기 → 게이트 통과해야 함
FakeGrader(offset=3)  → 망가진 채점기 → 게이트 fail 해야 함  ← 이게 핵심
ConstantGrader(3)     → 상수 채점기   → 절대 좋은 점수 받으면 안 됨
```

## 핵심 결정 1 — 위반을 모아서 한 번에 보고한다

예외를 즉시 던지지 않고 `list[str]`로 돌려준다.
CI 한 번에 무너진 곳을 다 봐야지, 하나 고치고 재실행하면 피드백 루프가 너무 길다.

## 핵심 결정 2 — 항목별로 본다

총점만 보면 어느 축이 무너졌는지 모른다. Grammar가 폭락하고 Vocabulary가 올라
평균이 그대로일 수 있다. 위반 메시지에 **항목 이름을 넣는다.**

## 핵심 결정 3 — 개별 실패를 모아서 보고한다

에세이 한 건 채점 실패로 예외를 올리지 않는다. 50건 배치가 한 건 때문에 죽으면
매번 처음부터 다시 돌려야 한다. 단 **실패율 자체가 게이트 판정 대상**이다(기본 허용 0%).

## 실패 모드

| 상황 | 처리 |
|---|---|
| 일부 채점 실패 | `report.failures`에 수집, 실패율로 게이트 판정 |
| 전부 실패 | `RuntimeError` — 이건 배치가 아니라 설정 문제다 |
| 항목 QWK 측정 불가 | 게이트 위반으로 처리 (조용히 통과 금지) |

## 측정 — 게이트가 실제로 작동하는가

`check_regression`을 무력화하는 뮤테이션을 넣어 **정확히 5건이 깨지는 것**을 확인했다.
게이트가 통과하는 걸 확인하는 건 검증이 아니다.

## CI 배치

| 잡 | 트리거 | LLM 호출 |
|---|---|---|
| `unit` | 모든 푸시 | 없음 (무료·빠름) |
| `regression` | `workflow_dispatch` 수동 | 있음 (유료) |

`pytest` 기본값이 `-m 'not regression'`이라 로컬에서 실수로 유료 호출이 나가지 않는다.
