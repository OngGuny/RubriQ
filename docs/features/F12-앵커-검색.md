# F12. 앵커 검색 (retrieve_anchors · pgvector RAG)

| | |
|---|---|
| 상태 | **미구현** |
| 단계 | T1 |
| 예정 코드 | `src/rubriq/tools/retrieve_anchors.py` · `scripts/ingest_anchors.py` |
| 의존 | F07 골든셋 (앵커 원천) |
| 인프라 | postgres + pgvector `:5432` 기동 확인됨 |

## 문제

루브릭 서술어는 **말로 된 기준**이라 필연적으로 모호하다.
"오류가 눈에 띈다"가 몇 개인지 정의할 수 없다.
→ 같은 에세이를 다시 채점하면 다른 점수가 나온다 (**일관성 σ가 커진다**)

## 해결 — 실물을 보여준다

각 점수대의 대표 답안(**앵커**)을 few-shot으로 붙인다.
'눈에 띄는 오류'를 말로 정의할 필요가 없어진다. 보면 안다.

## 계약

```python
retrieve_anchors(text: str, dimension: RubricDimension, k: int = 3)
    -> list[AnchorEssay]
# AnchorEssay: essay_id · text · score · dimension · similarity
```

## 설계

```
골든셋 → 항목별·점수대별 대표 답안 선별 → 임베딩 → pgvector 적재
                                                       │
채점 대상 에세이 → 임베딩 → 코사인 유사도 검색 ────────┘
                              → 점수대가 겹치지 않게 k개 선택
                                 → 프롬프트에 삽입
```

## 핵심 결정 1 — 유사도만으로 뽑지 않는다

가장 비슷한 3개를 뽑으면 **전부 같은 점수대**일 수 있다.
그러면 "이게 3점이다"만 알려주고 척도를 못 보여준다.
**점수대 다양성을 강제**한다 — 예: 낮음/중간/높음에서 각 1개.

## 핵심 결정 2 — 골든셋과 앵커를 분리한다

평가에 쓰는 50건을 앵커로도 쓰면 **정답을 프롬프트에 넣고 채점하는 셈**이다.
QWK가 부풀려진다. 앵커 풀은 골든셋과 겹치지 않게 별도로 확보한다.

> 이게 이 기능에서 가장 밟기 쉬운 함정이다.

## 핵심 결정 3 — 캐시 구조에 미치는 영향

앵커는 에세이마다 달라지므로 **완전 고정이 아니다.**
프롬프트가 3단계가 된다:

```
루브릭 (항상 고정)   ← 캐시
앵커   (준고정)      ← 경계 추가 필요
에세이 (가변)
```

현재 F04의 경계는 하나뿐이라 **확장이 필요하다** (ADR 003 「되돌리는 조건」).

## 비용

앵커는 에세이 전문이다. 3개만 넣어도 프롬프트가 크게 길어지고,
항목별 분리 호출(F13)이면 그 증가분이 6배로 곱해진다.

## 실패 모드

| 상황 | 처리 |
|---|---|
| pgvector 미기동 | 앵커 없이 진행 (degradation) + 플래그 |
| 앵커 풀 부족 | k를 줄여서 진행, 부족했음을 기록 |
| 유사도 전부 낮음 | 앵커를 안 넣는다 — 무관한 예시는 해롭다 |

## 측정 — 이건 가설이지 사실이 아니다

**"앵커가 분산을 줄인다"는 현재 가설이다.**
앵커 없이/있이 각각 골든셋을 돌려 **일관성 σ와 QWK를 비교**해야 안다.
효과가 없으면 비용만 늘린 것이므로 제거한다.
