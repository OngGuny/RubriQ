# F08. Langfuse 관측 · 트레이싱

| | |
|---|---|
| 상태 | **미구현** (인프라는 기동 완료) |
| 단계 | T0 |
| 예정 코드 | `src/rubriq/observability/langfuse.py` |
| 의존 | F05 LLM 클라이언트 · F04 프롬프트 레지스트리 |
| 인프라 | `docker/compose.yaml` — Langfuse `:3001` 기동 확인됨 |

## 문제

숫자가 나빠졌을 때 **어디서 무너졌는지** 알아야 한다.
최종 점수만 보면 전처리가 문제인지, 도구 출력이 이상한지, 채점 프롬프트가 문제인지 모른다.

## 계약

```
요청 1건 = trace 1개
  ├ span: 전처리
  ├ span: 사전 라우팅        (조기 반환 시 여기서 종료)
  ├ span: 도구 호출 ×3       (병렬)
  ├ generation: 항목별 채점 ×6  ← 프롬프트 버전·토큰·비용 기록
  ├ span: 일관성 검증
  └ generation: 피드백 생성
```

각 generation에 기록할 것: `prompt_id` · `fingerprint` · `model` · `effort` ·
`usage`(캐시 포함) · `latency_ms`.

## 설계

| 항목 | 방식 |
|---|---|
| 연결 | self-host (`docker compose`, 무료) |
| 주입 | `StructuredLLM` 래퍼 — 호출부를 안 고친다 |
| 프롬프트 등록 | 파일 → Langfuse 등록, 트레이스에 버전 링크 |
| 활성화 | `settings.langfuse_enabled` — 키 없으면 무동작 |

## 핵심 결정 1 — 트레이싱이 실패해도 채점은 계속된다

관측이 본 기능을 죽이면 안 된다. Langfuse 장애·키 누락 시 조용히 비활성화하고
채점은 그대로 진행한다. 단 **비활성화 사실은 로그에 남긴다** — 조용히 꺼진 관측은 없는 것보다 나쁘다.

## 핵심 결정 2 — PII와 원문 토큰을 남기지 않는 설계를 전제한다

에세이 본문은 학생 저작물이다. 지금은 개인 프로젝트라 공개 데이터셋만 쓰지만,
**무엇을 남기고 무엇을 남기지 않을지**를 처음부터 정해둔다.
트레이스에는 essay_id와 통계(길이·오류 수)를 남기고 본문은 선택적으로 둔다.

## 핵심 결정 3 — 마커 처리 미정

프롬프트 파일의 `<!-- CACHE_BOUNDARY -->`는 비표준 문법이다.
Langfuse에 등록할 때 (a) 마커 포함 원문 그대로 (b) 두 블록을 분리 등록 중 미정.
(b)가 맞아 보이지만 버전 관리 단위가 둘로 갈리는 문제가 있다.

## 산출물

- 재채점 루프가 발동한 케이스의 트레이스 (F14가 생긴 뒤)
- 프롬프트 버전별 성능 비교 (F04 지문과 대조)

## 측정

트레이스가 **실제로 재현에 쓸모 있는지**는 `docs/failures/` 3건을 쓸 때 판명된다.
"트레이스를 붙였다"가 아니라 "트레이스로 원인을 찾았다"가 이 기능의 완료 조건이다.
