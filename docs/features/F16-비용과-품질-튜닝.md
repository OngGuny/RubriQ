# F16. 비용·품질 튜닝 (모델 라우팅 · 프롬프트 캐싱)

| | |
|---|---|
| 상태 | **미구현** (비용 계산만 구현) |
| 단계 | T2 |
| 예정 코드 | `src/rubriq/llm/router.py` |
| 의존 | F05 비용 계산 · F13 항목별 채점 |
| 관련 | ADR 003 |

## 문제

F13이 호출을 6배로 늘렸다. **그 대가를 정당화해야 한다.**

## 두 개의 레버

```
캐싱  — 품질을 안 건드리고 비용만 줄인다      ← 먼저 한다 (공짜 이득)
라우팅 — 품질과 비용을 맞바꾼다               ← 나중에 한다 (트레이드오프)
```

**순서가 중요하다.** 공짜 이득을 다 쓰기 전에 품질을 거래하면 손해다.

## 레버 1 — 프롬프트 캐싱

구조는 F04에서 이미 갖췄다. 여기서는 **측정**한다.

| 측정 | 방법 |
|---|---|
| 캐시 실제 적중 | `usage.cache_read_input_tokens` > 0 |
| 비용 절감폭 | `--no-cache` on/off 동일 골든셋 비교 |
| latency 영향 | p50 / p95 전후 |

**검증 수단이 이것뿐이다.** 캐시 미스는 에러를 내지 않으므로
`cache_read_input_tokens`가 0인지 보지 않으면 영원히 모른다.

### 함정 — 최소 프리픽스가 모델마다 다르다

| 모델 | 최소 | 현재 system(~900토큰) |
|---|---:|---|
| Claude Opus 5 | 512 | 캐시됨 ✅ |
| Claude Sonnet 5 | 1024 | **안 됨** ❌ |
| Haiku 4.5 | 4096 | **안 됨** ❌ |

**세대 순이 아니다.** 이게 다음 레버와 충돌한다.

## 레버 2 — 모델 라우팅

항목별로 품질 민감도가 다르다는 가설:

| 항목 | 가설 | 후보 |
|---|---|---|
| Conventions (철자·구두점) | 도구 출력이 대부분 하므로 판단이 단순 | 경량 |
| Grammar | 도구 출력 + 판단 | 중간 |
| Cohesion / Phraseology | 순수 판단, 미묘함 | 고성능 |

### 핵심 결정 — 라우팅이 캐싱을 죽일 수 있다

"싼 항목은 Haiku로"를 하면 **그 항목은 캐시가 안 된다** (최소 4096토큰).
단가는 1/5인데 매 호출 900토큰을 full price로 낸다.

```
Opus 5  + 캐시 히트:  900토큰 × $5/M × 0.1 = $0.00045
Haiku   + 캐시 미스:  900토큰 × $1/M × 1.0 = $0.00090   ← 2배 비싸다
```

**라우팅 비용 계산에 캐시 적중 여부를 반드시 포함해야 한다.**
단가표만 보고 라우팅하면 오히려 비싸진다.

## 판정 기준

라우팅은 **QWK 하락이 임계치 이내일 때만** 채택한다.
비용이 절반이어도 QWK가 0.1 떨어지면 안 쓴다.
"싸게 만들었다"가 아니라 **"품질을 유지하며 싸게 만들었다"** 여야 한다.

## 아직 모르는 것

- 항목별 품질 민감도는 **가설이다.** 측정 전에는 어느 항목이 경량 모델로 충분한지 모른다.
- effort 스윕(low~max)도 같은 축의 레버인데 아직 안 건드렸다. 모델을 바꾸기 전에
  **같은 모델 낮은 effort**를 먼저 재보는 게 순서다.
