## 문제

채점은 **느리다.** 도구 3종 + 항목별 6회 + 검증 + 피드백이면
수십 초가 걸린다. 그 동안 아무것도 안 보이면 쓸 수 없다.

## 계약

```
POST /grade          → GradingResult (동기, 배치용)
POST /grade/stream   → SSE 진행 상황 + 최종 결과
GET  /health
```

## 설계 — 스트리밍 단위

토큰 단위가 아니라 **노드 단위**로 흘린다.

```
event: progress   {"stage": "preprocess", "done": true}
event: progress   {"stage": "tools", "done": true}
event: score      {"dimension": "grammar", "score": 3}
event: progress   {"stage": "verify", "regrade": 1}
event: result     {최종 GradingResult}
```

**부분 응답은 스키마 검증을 못 한다.** 그래서 중간 이벤트는 진행 상황만 보내고,
검증된 최종 결과는 마지막 `result` 이벤트에 담는다.
이 구조가 설계 제약이고, 클라이언트와 먼저 합의해야 할 지점이다.

## 핵심 결정 1 — async에서 동기 블로킹을 오프로드한다

`grammar_check`(F11)는 **LanguageTool 동기 라이브러리**다.
async 엔드포인트에서 그냥 호출하면 이벤트 루프가 막혀
**그 워커의 모든 요청이 함께 지연된다.**

```python
errors = await asyncio.to_thread(grammar_check, text)
```

LLM 호출은 I/O 대기가 지배적이라 async로 동시성을 벌 수 있지만,
블로킹 하나가 그 이점을 통째로 없앤다.

## 핵심 결정 2 — Depends로 의존성을 주입한다

설정·LLM 클라이언트·그래프 인스턴스를 엔드포인트 시그니처에서 선언적으로 받는다.
실질적 이점은 **테스트에서 교체 가능**하다는 것 — `FakeLLM`을 주입해
API 레이어를 LLM 없이 테스트한다.

## 핵심 결정 3 — uvicorn + gunicorn 조합

| | 역할 |
|---|---|
| ASGI | 비동기 인터페이스. FastAPI가 ASGI 앱 |
| uvicorn | ASGI 서버 |
| gunicorn | 프로세스 매니저 — uvicorn worker를 여러 개 |

멀티코어 활용과 워커 재시작 관리 때문에 실운영은 이 조합을 쓴다.
**워커 수를 잘못 잡으면 async 이점이 사라진다** — LLM 대기가 지배적이라
CPU 코어 수보다 많은 워커가 유리할 수 있고, 이건 측정해야 안다.

## Docker

```
docker/Dockerfile      멀티스테이지 (uv sync → 런타임)
docker/compose.yaml    postgres+pgvector · Langfuse (이미 있음)
```

LanguageTool이 JVM을 요구하면 이미지가 커진다 —
별도 서비스로 뺄지 이미지에 넣을지 결정 필요.

## 실패 모드

| 상황 | 처리 |
|---|---|
| 스트림 중 채점 실패 | `event: error` 후 종료 — 침묵하지 않는다 |
